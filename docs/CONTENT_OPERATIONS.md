# 콘텐츠 운영·삭제·정정 절차

GamePickup은 공식 원문을 짧게 요약하고 원문으로 연결하는 서비스다. 원문 전문을
재게시하지 않으며, 권리자·사용자가 요청하면 공개 노출을 먼저 멈추고 사실관계를
확인한다. 이 문서는 1인 운영 MVP의 기본 처리 기준이다.

## 상태와 책임

1인 운영 기준 책임자는 **서비스 운영자 1명**으로 고정한다. 운영자는 매일 09:00
KST에 검수 큐·수집 상태·푸시 실패를 확인하고, 긴급 권리/오보 건은 발견 즉시
처리한다. 주 1회(월요일)에는 소스별 중복률·수정률·회수 건수와 데드링크를
기록한다. 부재 시 자동 발행을 끄고 URL 직접 등록만 허용한다.

| 상태 | 공개 여부 | 운영 의미 |
|---|---:|---|
| `draft` | 아니오 | 수집·URL 등록 직후. 요약 품질과 권리 필드를 확인한다. |
| `reviewed` | 아니오 | 검수 완료 또는 회수된 콘텐츠. 예약 발행 전 대기 상태다. |
| `published` | 예 | 공식 원문 링크와 요약을 앱에 노출한다. |
| 삭제 | 아니오 | 잘못된 항목·중복·권리 요청으로 영구 노출을 중단한다. 감사 로그는 보존한다. |

발행·회수·삭제·수집 소스 변경·관리자 로그인 성공은 `audit_logs`에 기록한다.
비밀번호, JWT, 설치 시크릿, 원문 수집 헤더는 감사 로그에 저장하지 않는다.

## 삭제·정정 요청 처리

1. `PRIVACY_CONTACT_EMAIL`로 들어온 요청에 접수 시각, 요청자, 원문 URL, 대상 콘텐츠 ID,
   요청 사유를 기록한다. 이메일 주소 등 개인정보는 운영 메모에 최소한으로 남긴다.
2. 긴급 권리·개인정보·명백한 오보 요청은 24시간 안에 해당 콘텐츠를 `reviewed`로
   회수하고 자동 발행 소스를 일시 중지한다.
3. 일반 정정·삭제 요청은 영업일 3일 안에 공식 원문과 요청 근거를 대조한다.
4. 사실 오류는 관리자에서 요약·날짜·이미지를 수정한 뒤 다시 검수한다. 권리 또는
   출처 문제가 확인되면 원문 링크를 포함한 공개 콘텐츠를 삭제한다.
5. 처리 결과와 근거를 요청자에게 회신하고, 콘텐츠 ID·처리자·시각·결과를 감사 로그와
   운영 기록에 남긴다. 원문 전문이나 불필요한 개인정보는 보관하지 않는다.

## 수집 소스 장애·오탐 대응

- 3회 연속 실패 또는 5회 연속 0건이면 source health 경고를 확인한다.
- 셀렉터/API 변경이 의심되면 `auto_publish=false`로 바꾸고 새 항목을 검수 모드로
  둔다. 기존 발행물은 근거가 확인될 때까지 회수하지 않는다.
- 관리자 dry-run에서 제목·날짜·원문 URL을 확인한 뒤 소스를 수정한다.
- 잘못 발행된 항목은 즉시 회수하고 원인을 기록한다. 자동 발행 소스에서 회수가
  발생하면 시스템이 해당 소스를 검수 모드로 강등한다.
- 수정 후 정상 항목 5건 이상을 수동 확인하고, 첫 운영 주간에는 자동 발행을 다시
  켜지 않는다. 신뢰 소스 승격은 무수정 승인 20건 이상·수정/회수 0건을 기준으로
  운영자가 최종 결정한다.

## 검수 큐 처리 기준

| 우선순위 | 대상 | 처리 목표 | 기본 조치 |
|---|---|---:|---|
| P0 | 권리 침해·개인정보·명백한 오보 | 24시간 이내 | 즉시 비공개/소스 자동 발행 중지 |
| P1 | 잘못된 날짜·중복·요약 오류 | 영업일 3일 이내 | 수정 후 재검수 또는 삭제 |
| P2 | 표현 다듬기·이미지 교체 | 다음 주간 점검 | 수정 후 검수 |

처리자는 `audit_logs`의 콘텐츠 ID·이전/이후 상태·근거 URL·처리 시각을 확인하고,
주간 기록에는 전체 draft 수, 무수정 승인 수, 수정 승인 수, 회수 수를 남긴다.
첫 주 자동 발행 승격 여부는 **무수정 승인 20건 이상이고 수정·회수 0건**일 때만
운영자가 결정한다.

## 소스 설정 버전과 롤백

소스 설정을 변경할 때마다 관리자 운영 기록에 다음을 남긴다.

1. 소스 ID, 변경 전/후 `source_type`·endpoint·selector/API 매핑, 변경 사유와 시각
2. 변경 전 설정 JSON과 dry-run 결과(정상 5건·빈 응답·중복)를 보관
3. 배포 직후 첫 실행 결과를 확인하고, 제목·날짜·원문 URL이 깨지면 즉시
   `auto_publish=false`로 전환한다.
4. 롤백은 직전 설정 JSON을 다시 저장하고 dry-run을 통과한 뒤 자동 발행을 재개한다.

운영자는 설정 버전을 `YYYYMMDD-N` 형식으로 기록하며, 마지막 정상 버전 하나는
항상 복구 가능한 형태로 보관한다. collector를 사용하지 않는 수동 출시에서는
이 절차 대신 URL·권리 근거·검수자를 콘텐츠별로 기록한다.

## 출시 첫 주 운영 기준

- 실제 공식 소스는 게임별 1개부터 등록하고 `dry-run` 결과를 보관한다.
- 모든 새 소스는 수동 검수로 시작한다. 자동 발행은 품질·권리 확인 뒤 단계적으로
  승격한다.
- 매일 09:00 KST에 수집 실패, 검수 큐, 발행 회수, 푸시 실패를 확인한다.
- 매주 중복률·정정률·원문 데드링크·무수정 승인률을 기록하고 소스별 허용 필드를
  갱신한다. 자동 발행은 무수정 승인 20건·수정/회수 0건을 충족하기 전까지 켜지 않는다.

## 개인정보 보존 검토

- 현재 앱은 설치 해지 시 즉시 푸시 토큰·관심 게임 연결을 끊지만, 설치 레코드와
  문의 원문을 자동 삭제하지 않는다. 운영자가 되돌릴 수 없는 파기를 승인하기 전까지
  보존기간과 법적 의무를 확인한다.
- 매월 1회 해지 후 장기 미사용 설치와 답변 완료 문의를 목록으로 검토한다. 실제
  자동 파기를 도입할 때는 보존기간(기본값), 예외, 백업 삭제 시점, 복원 불가 여부를
  먼저 결정하고 별도 마이그레이션·리허설을 거친다.
- 개인정보처리방침의 보존기간은 운영자가 실제로 지킬 수 있는 값만 기재한다.

## 운영자가 보관할 증적

- 소스별 공식 URL, 이용약관/robots 확인일, 허용 필드
- 이미지 권리 상태와 출처 URL
- dry-run 결과와 selector/API 버전
- 삭제·정정 요청 및 처리 결과
- 배포 전후 `/health/live`, `/health/ready`, 관리자 발행·앱 표시 스모크 결과
