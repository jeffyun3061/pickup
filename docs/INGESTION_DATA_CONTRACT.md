# 수집 데이터 계약과 출처별 차이 처리

GamePickup은 사이트별 원문 구조를 앱이나 PostgreSQL 테이블에 그대로 넣지 않는다.
각 수집기는 자기 형식을 `CollectedItem`으로 변환한 뒤, 서버의 공통 Ingest 계약으로
전달한다. 따라서 RSS가 XML이고 공개 API가 JSON이며 일부 사이트가 HTML이어도 앱의
조회 계약과 상태 머신은 변하지 않는다.

## 표준 항목

| 필드 | 의미 | 필수/규칙 |
|---|---|---|
| `source_id` | 등록된 공식 출처 | 필수. 소스별 설정·실행 이력과 연결 |
| `game_id` | GamePickup 카탈로그 게임 | 필수. 알 수 없는 게임은 저장하지 않음 |
| `external_id` | 출처가 제공하는 글 ID 또는 안정적인 URL | 필수. 멱등 키의 원재료 |
| `title` | 공지 제목 | 필수. 비어 있으면 건너뜀 |
| `url` | 공식 원문 링크 | 필수. 앱은 요약과 함께 원문으로 연결 |
| `summary` | 목록에서 얻은 짧은 설명 | 선택. HTML 노이즈 제거 후 사용 |
| `published_at` | 출처의 발행 시각 | 선택. RFC822/ISO/날짜 표기를 ISO로 정규화 |
| `image_url` | 이미지 후보 URL | 선택. 권리 검수 전에는 앱에 노출하지 않음 |

서버는 여기에 `kind`, `summary_points`, `raw_text`(최대 8천자),
`origin_published_at`, `idempotency_key`를 추가해 `draft`로 저장한다. 수집기는
발행 권한을 갖지 않으며, LLM 요약 실패나 형식 이상도 검수 큐에서 확인할 수 있다.

## 출처별 어댑터

- RSS/Atom: `guid`/`id`를 우선하고 없으면 링크를 ID로 사용한다.
- JSON API: `items_path`, `id_field`, `title_field` 등 매핑 설정으로 필드를 읽는다.
- HTML: 목록·제목·링크·날짜 CSS 셀렉터를 소스 설정으로 주입한다. JS 렌더링이
  필요한 경우 공개 DOM만 읽으며, 로그인·CAPTCHA 우회는 하지 않는다.

사이트가 바뀌면 공통 모델을 고치는 대신 해당 소스의 설정/어댑터만 수정한다.
관리 콘솔의 테스트 수집(dry-run)으로 제목·날짜·원문 링크를 확인하고, 0건·연속
실패가 감지되면 자동 발행을 검수 모드로 내린다.

## 중복·재시도·장애 경계

멱등 키는 `source_id + external_id` 범위로 서버에서 유일하게 만든다. ETag/Last-
Modified 또는 본문 해시가 같으면 파싱을 건너뛰고, 네트워크 재시도에도 같은 초안이
두 번 생기지 않는다. collector는 API와 별도 프로세스라 한 사이트 장애가 앱 API의
응답을 막지 않는다.

## 왜 MongoDB를 추가하지 않는가

앱 조회·게임별 필터·발행 상태·푸시 outbox·설치별 랭킹은 관계와 트랜잭션이 중요한
데이터라 PostgreSQL 한 엔진이 적합하다. 사이트별 설정과 LLM 분석처럼 형태가
가변적인 값은 PostgreSQL의 JSON 형태 필드(현재는 마이그레이션 호환을 위해 JSON
문자열)로 격리한다. 원문 전문을 무제한 보관하지 않고 요약에 필요한 텍스트만
제한한다.

MongoDB를 지금 추가하면 이중 쓰기, 백업·복구·모니터링, 데이터 정합성 비용이 늘어난다.
원문 대량 보관이나 별도 전문 검색이 실제 병목이 될 때만 오브젝트 스토리지와 검색
엔진을 독립적으로 추가하며, 그때도 공개 앱의 PostgreSQL 계약은 유지한다.
